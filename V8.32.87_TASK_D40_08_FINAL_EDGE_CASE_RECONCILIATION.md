## 2. SEC-11 — CORRECT CLIENT DISCONNECT DETECTION IN NODE.JS V24.19.0

### 2.1 Node.js v24.19.0 HTTP Lifecycle Semantics Analysis

In Node.js v24.19.0 (`node:http` implementation based on `stream.Readable` and `stream.Writable`), request and response lifecycles follow distinct event progressions:

| Object / Property | Event / State | Trigger Condition | Semantics During Inference | Premature Disconnect vs. Normal Complete |
| :--- | :--- | :--- | :--- | :--- |
| **`http.IncomingMessage` (`req`)** | `'close'` | Fired when the underlying stream/socket has closed. In HTTP/1.1 without keep-alive, or when the request stream completes, this can emit when the body is fully read. | **AMBIGUOUS**. In newer Node streams, `req.on('close')` fires whenever the readable side is destroyed, which can occur normally upon request body consumption. | **UNSAFE** as a standalone abort indicator. |
| **`http.IncomingMessage` (`req`)** | `'aborted'` | Deprecated in Node.js v17+. Emitted when the request was aborted by the client. | **DEPRECATED**. Should not be used in modern Node.js v24 runtimes. | Deprecated. |
| **`http.IncomingMessage` (`req.destroyed`)** | Boolean property | True if the readable stream has been destroyed. | Becomes `true` upon normal stream consumption or socket drop. | Does not indicate whether the response was completed. |
| **`http.ServerResponse` (`res`)** | `'close'` | Fired when the underlying stream/connection was terminated before `response.end()` was called, or when the response finishes. | Emits both on premature client disconnect **AND** after normal response completion. | **CRITICAL:** Must be paired with `!res.writableEnded` or `!res.writableFinished`. |
| **`http.ServerResponse` (`res`)** | `'finish'` | Fired when the last segment of the response headers and body have been handed off to the operating system network subsystem. | Normal completion. | Indicates successful response handoff. |
| **`res.writableEnded`** | Boolean property | Set to `true` synchronously when `res.end()` is invoked. | `false` while inference is running; `true` once gateway sends the HTTP response. | **AUTHORITATIVE GUARD**. If `res` emits `'close'` while `res.writableEnded === false`, the client disconnected prematurely! |
| **`res.writableFinished`** | Boolean property | Set to `true` after all data has been flushed to the underlying system. | `false` during inference. | Confirms physical transmission to the socket. |
| **`req.socket` / `res.socket`** | `'close'` | Emitted when the physical TCP socket completely closes. | Fired if client resets TCP connection (RST/FIN). | Low-level transport indicator. |

### 2.2 Precise Event Registration and Abort Condition

The correct, production-grade pattern in Node.js v24.19.0 to detect premature client disconnection during asynchronous inference without falsely aborting valid requests is:

```javascript
// 1. Instantiate dedicated AbortController
const abortController = new AbortController();

// 2. Define the disconnect listener on res ('close')
const onClientDisconnect = () => {
    // If the client closes the HTTP connection before res.end() has been called,
    // this is a premature client drop.
    if (!res.writableEnded) {
        logPhase(requestId, 'PILOT_CLIENT_DISCONNECTED_PREMATURE', {
            active_concurrency: activeInferences
        });
        abortController.abort(new Error('CLIENT_DISCONNECTED_PREMATURELY'));
    }
};

// 3. Register listener on ServerResponse 'close'
res.on('close', onClientDisconnect);

// 4. Pass signal to outbound inference (Axios / Fetch)
try {
    const lmResponse = await axios.post(lmStudioUrl + '/v1/chat/completions', lmPayload, {
        headers: { 'Content-Type': 'application/json' },
        timeout: effectiveTimeoutMs,
        signal: abortController.signal
    });
    // ... post-processing and commit ...
} finally {
    // 5. Unconditional listener cleanup
    res.removeListener('close', onClientDisconnect);
}
```

### 2.3 Distinction Between Normal Completion and Premature Disconnect

1. **Normal Flow:**
   - Request body parsed $\to$ inference dispatched $\to$ inference completes $\to$ review record committed $\to$ gateway calls `res.status(200).json(...)`.
   - `res.status(200).json(...)` invokes `res.end()`, which sets `res.writableEnded = true` synchronously.
   - When the socket subsequently finishes or closes, `res.on('close')` fires.
   - The condition `!res.writableEnded` evaluates to `false`. **Zero abort is triggered.**
2. **Premature Disconnect Flow:**
   - Client terminates TCP connection / closes tab while inference is in flight.
   - Socket drops. Node.js destroys the response stream.
   - `res.on('close')` fires.
   - Because `res.end()` was never called, `res.writableEnded === false`.
   - The condition evaluates to `true`.
   - `abortController.abort()` cancels the outbound Axios/LM Studio socket immediately.
   - Inflight inference terminates, freeing the concurrency slot.

## 3. SEC-10 — COMPLETE IPV6 & LOOPBACK CANONICALIZATION SPECIFICATION

### 3.1 Deficiencies of Pure Regex Matching

A naive regular expression such as `^::ffff:7f` or `127\.0\.0\.1` is vulnerable to alternative syntactic encodings permitted by RFC 4291 and RFC 5952:
- Zero-compressed IPv4-mapped notation: `::ffff:7f00:1`
- Uncompressed zero segments: `0:0:0:0:0:ffff:7f00:1`
- Zero-padded segments: `0000:0000:0000:0000:0000:ffff:7f00:0001`
- Uppercase hexadecimal: `::FFFF:7F00:1`
- Dotted-quad mixed format: `::ffff:127.0.0.1`
- Bracketed URI hosts: `[::ffff:7f00:1]`
- Scoped/Zone IDs: `fe80::1%eth0`

### 3.2 Canonical Multi-Stage IP Resolution and Validation Strategy

Rather than relying on brittle string regular expressions, the canonical parsing architecture uses a multi-stage validation algorithm:

```
[ Raw Hostname / IP Input ]
             |
             v
   1. Strip Enclosing Brackets: '[' ... ']' -> Raw IP / Host
             |
             v
   2. Strip Scope / Zone ID: split('%')[0]
             |
             v
   3. Check Node.js net.isIP(cleanHost):
      [Return 4] ---> IPv4 Parsing Stage (Check 127.0.0.0/8)
      [Return 6] ---> IPv6 Canonicalization Stage
      [Return 0] ---> Hostname Classification Stage
```

#### Stage A: IPv4 Check (`net.isIP(host) === 4`)
- Split by `.`. Parse octets $O_1, O_2, O_3, O_4$ as decimal integers.
- If $O_1 === 127$, the address is in `127.0.0.0/8` $\implies$ **LOOPBACK DETECTED**.

#### Stage B: IPv6 Canonicalization (`net.isIP(host) === 6`)
Every IPv6 address can be parsed into eight 16-bit unsigned integer words $[W_0, W_1, \dots, W_7]$:
1. Handle `::` expansion by inserting $(8 - \text{explicit\_words})$ zero words.
2. If the last two words represent IPv4-mapped notation (`W_4 === 0` or omitted, `W_5 === 0xffff`):
   - In dotted-decimal suffix (`::ffff:127.0.0.1`), convert to two 16-bit words: $W_6 = (127 \ll 8) + 0 = \text{0x7f00}$, $W_7 = (0 \ll 8) + 1 = \text{0x0001}$.
   - In hex quad suffix (`::ffff:7f00:1`), $W_6 = \text{0x7f00}$, $W_7 = \text{0x0001}$.
3. **Loopback Conditions:**
   - **Pure IPv6 Loopback (`::1`):** $W_0=W_1=W_2=W_3=W_4=W_5=W_6=0$ and $W_7=1$.
   - **IPv4-Mapped Loopback:** $W_0=W_1=W_2=W_3=W_4=0$, $W_5=\text{0xffff}$, and $(W_6 \gg 8) === 127$.

#### Stage C: Hostname Classification (`net.isIP(host) === 0`)
1. **Loopback Hostname Check:**
   - If `host.toLowerCase() === 'localhost'` or `host.toLowerCase().endsWith('.localhost')` $\implies$ **LOOPBACK DETECTED**.
2. **Public / External DNS Hostnames:**
   - If `host` is a valid DNS hostname (e.g., `api.example.com`, `models.internal`):
   - **Do NOT reject immediately merely because it is non-numeric.**
   - **DNS Resolution Check (Anti-SSRF / Anti-DNS-Rebinding):** Before opening a connection, resolve the hostname using `dns.promises.lookup(host, { all: true })`.
   - If **any** returned IP address resolves to a loopback address (`127.0.0.0/8`, `::1`, or IPv4-mapped loopback), intercept and block with `SecurityAssertionError`.

### 5.3 Proof Against Inconsistent State
In an in-memory single-threaded JavaScript event loop:
1. Operations between Stage 4 and Stage 6 execute synchronously in a single call stack frame without yielding to the microtask queue or I/O loop (`await`).
2. Any synchronous exception triggers an enclosing `try ... catch` block that deletes `RequestIdIndex`, deletes `ReviewRepository`, and releases `ReservationMap` in reverse order before re-throwing.
3. Therefore, it is mathematically impossible for another asynchronous request to observe a review record in `ReviewRepository` while its reservation is uncommitted or its `request_id` index is missing.
