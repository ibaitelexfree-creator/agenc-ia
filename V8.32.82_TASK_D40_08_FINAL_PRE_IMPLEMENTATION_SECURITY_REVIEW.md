### 2.1 The Mandatory 11-Step Extraction Pipeline

```
[Supervised Runner / Client]
       │
       ▼
 [Step 1: Auth & Legacy Route Gate]
   ├── Route Check: If route is /v1/inference and task_type === 'EXTRACTION' ──► REJECT (HTTP 400) [No Model Dispatch]
   ├── Route Check: Extraction allowed ONLY on /v1/pilot/inference
   └── Verify x-internal-service-token via constant-time timingSafeEqual
       │
 [Step 2: Request Schema & Idempotency Check]
   ├── Enforce task_type === 'EXTRACTION'
   ├── Validate pilot-request-schema.json
   └── Check ReviewRepository: If candidate for source_message_id already exists ──► REJECT (HTTP 409) [No Model Dispatch]
       │
 [Step 3: Authoritative Source Retrieval]
   ├── Query SyntheticSourceRepository.getById(synthetic_fixture_id)
   ├── Validate request source_message_id and conversation_id against repository record
   ├── Discard any caller-supplied source_text or source_hash
   └── Compute authoritative SHA-256 source hash inside trusted gateway memory
       │
 [Step 4: Model Inference Dispatch]
   └── Send prompt messages to Mock LM Studio (or LM Studio in controlled test environment)
       │
 [Step 5: Output Syntax Validation]
   ├── Parse JSON (direct or fenced markdown block)
   └── If malformed JSON ──► REJECT (HTTP 502 INVALID_MODEL_OUTPUT) [Zero Storage]
       │
 [Step 6: Forbidden Field Audit (Model Immune Check)]
   └── Reject if output contains: human_review, review_status, approval_status,
       approved, reviewer_id, reviewed_by, reviewed_at, is_approved, status
       ──► REJECT (HTTP 502 SECURITY_VIOLATION) [Zero Storage]
       │
 [Step 7: Candidate Schema & Identity Verification]
   ├── Validate against pilot-candidate-extraction-schema.json
   └── Ensure candidate source_message_id & conversation_id match repository record exactly
       ──► If mismatch ──► REJECT (HTTP 502 UNTRUSTED_IDENTITY_MISMATCH) [Zero Storage]
       │
 [Step 8: Cryptographic Provenance Verification]
   ├── For every claim in verifiable_claims:
   │   ├── Verbatim substring check against authoritative source_text
   │   ├── UTF-16 code unit offset verification (substring(start, end) === exact_quote)
   │   └── Grounding status = SOURCE_GROUNDED
   └── ALL-OR-NOTHING: If 1 claim fails ──► REJECT (HTTP 502 PROVENANCE_FAILED) [Zero Storage]
       │
 [Step 9: Canonical Review Record Construction]
   └── Trusted application code wraps candidate into CanonicalReviewRecord:
       - human_review.status = 'PENDING_REVIEW'
       - human_review.reviewed_by = null
       - human_review.reviewed_at = null
       │
 [Step 10: Atomic Storage in ReviewRepository]
   ├── Atomic check-and-insert into in-memory Map with defensive structuredClone()
   └── If concurrency race or storage failure ──► REJECT (HTTP 500 / 409) [Zero Partial Acceptance]
       │
 [Step 11: HTTP 200 Delivery]
   └── Emit HTTP 200 SUCCESS with candidate_id, record_id, and review_status: 'PENDING_REVIEW'
```

## 3. Detailed Specifications for SEC-01 through SEC-06

### SEC-01: Legacy Route Extraction Bypass Prevention

- **Problem:** In earlier revisions, `/v1/inference` treated any prompt as a general completion. If a caller sent an extraction request through `/v1/inference`, the model could generate extraction text, returning unverified claims and bypassing provenance and review storage.
- **Rule:**
  1. `/v1/inference` inspects `req.body` immediately following authentication.
  2. If `req.body.task_type === 'EXTRACTION'`, or if `req.body.synthetic_fixture_id` is present, or if the system prompt / prompt requests structured candidate extraction matching extraction schemas, `/v1/inference` immediately aborts:
     ```json
     {
       "status": "ERROR",
       "error_type": "EXTRACTION_ROUTE_REJECTED",
       "error": "Extraction requests are strictly prohibited on /v1/inference. Use dedicated /v1/pilot/inference route.",
       "requestId": "req-..."
     }
     ```
  3. HTTP Status: `400 Bad Request`.
  4. Under zero circumstances is an extraction prompt dispatched to LM Studio via `/v1/inference`.
  5. Standard legacy text completions (e.g. `prompt: "Ping test"`) continue to function without alteration.

### SEC-02: Test Network Guard Specification

- **Protected Target:** `127.0.0.1:1234` (and `localhost:1234`, `[::1]:1234`).
- **Intercepted Layers:**
  1. `http.request` and `http.get`
  2. `https.request` and `https.get`
  3. `net.Socket.prototype.connect`
  4. Global `fetch` (via Undici agent / dispatcher override)
- **Mechanism:**
  - Before a TCP socket initiates a 3-way handshake or resolves DNS, the intercepted hook parses the destination host and port.
  - If `(host === '127.0.0.1' || host === 'localhost' || host === '::1') && port === 1234`, the hook synchronously throws a custom unhandled `SecurityAssertionError('BLOCKED_NETWORK_CALL: Connection to live LM Studio 127.0.0.1:1234 is strictly forbidden in test execution')` and destroys the socket immediately.
  - The guard registers a call counter `guard.blockedAttempts` allowing tests to assert that an attempted call was intercepted.
- **Activation Scope & Limitations:**
  - Activated by importing `test-network-guard.js` at the top of test files.
  - **Process Boundary:** Intercepts connections within the current Node.js process and thread. Does **not** intercept detached subprocesses unless spawned with `NODE_OPTIONS="--import ..."` or `--require`.
  - In our architecture, all tests and gateway instances execute within the test harness process or child processes instrumented with the guard.

### SEC-03: Fixture and Source Identifier Contract

- **Authoritative Entity Hierarchy:**
  1. `synthetic_fixture_id`: Primary key of approved in-memory fixture (`SYNTHETIC_001`, `SYNTHETIC_002`).
  2. `source_message_id`: Extracted from the authoritative fixture record (`{ type: "integer", value: "1001" }`).
  3. `conversation_id`: Extracted from the authoritative fixture record (`{ type: "text", value: "34612345678@s.whatsapp.net" }`).
  4. `source_text`: The verbatim message string stored inside the fixture record.
  5. `source_hash`: Cryptographically computed UTF-8 SHA-256 digest of `source_text` calculated by the repository.
- **Contract Rules:**
  - Caller provides `synthetic_fixture_id`. Caller may optionally provide `source_message_id` and `conversation_id` for correlation verification.
  - If caller-provided IDs do not match the repository's record, the request is rejected with `422 Unprocessable Entity` before inference dispatch.
  - Caller is **prohibited** from supplying `source_text` or `source_hash`. Any caller-supplied `source_text` is ignored or rejected.
- **Repository Signatures:**
  ```javascript
  class SyntheticSourceRepository {
    getById(fixtureId: string): {
      fixture_id: string;
      source_message_id: { type: 'integer' | 'text'; value: string };
      conversation_id: { type: 'integer' | 'text'; value: string };
      source_text: string;
      source_hash: string;
      utf16_length: number;
      byte_length: number;
    } | null;
  }
  ```

- **HTTP Response Envelope (`/v1/pilot/inference`):**
  - `status`: `"SUCCESS"` (reflects the HTTP pipeline operational outcome).
  - `review_status`: `"PENDING_REVIEW"` (mirrors `record.human_review.status`).
  - `record_id`: `"rec-..."` (pointer to the stored repository record).
  - `result`: Contains the validated claims and candidate details.
  - `error`: `null`.

### SEC-05: Duplicate & Idempotency Behavior

- **Candidate Uniqueness:** A source message can have at most **one** active pending extraction candidate in the current cycle.
- **Natural Key:** Composite key `(fixture_id, source_message_id.value)`.
- **Sequential Duplicate:** If a second extraction request is submitted for the same fixture/source message, the Gateway checks `ReviewRepository.has(key)`. If true, it returns `HTTP 409 Conflict`:
  ```json
  {
    "status": "DUPLICATE_EXTRACTION_CANDIDATE",
    "error": {
      "code": "DUPLICATE_EXTRACTION_CANDIDATE",
      "message": "A pending review candidate already exists for this source message.",
      "existing_record_id": "rec-...",
      "fixture_id": "SYNTHETIC_001"
    }
  }
  ```
  Zero model inference is dispatched for duplicate requests.
- **Concurrent Duplicate:** Synchronous JavaScript execution guarantees that during insertion, atomic reservation occurs. If two requests race, the first successfully sets the map entry; the second detects the collision and yields HTTP 409.
- **Durability Limitation:** Stored in Node.js memory (`Map`). Process restart clears all entries. This is explicitly documented and not claimed to be durable SQLite persistence.

### SEC-06: Storage Concurrency Limitations

- **In-Memory Concurrency Model:** Single-process Node.js event-loop atomicity.
- **Guarantees:**
  - Synchronous operations (`has()`, `get()`, `set()`, `delete()`) on `Map` execute without context switching between JavaScript statement boundaries.
  - Deep cloning via `structuredClone()` ensures zero reference leakage to external callers.
- **Disclaimers (What is NOT guaranteed):**
  - No cross-process synchronization (multiple cluster workers will each have separate memory).
  - No thread-safe shared memory (not designed for `worker_threads` sharing `SharedArrayBuffer`).
  - No persistent cross-restart durability.
