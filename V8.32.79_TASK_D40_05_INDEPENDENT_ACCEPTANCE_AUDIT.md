## 4. Forensic Investigation of the 36 vs 35 Test Discrepancy

### 4.1 Root Cause of the Numbering Discrepancy
The discrepancy between "36 tests" and the 35 numbered items in Section 8.2 of V8.32.78 is caused by two compounding factors:

1. **Node.js Test Runner TAP Counting:**
   In Node's native test runner (`node:test`), the top-level test block:
   ```javascript
   test('PILOT-001 Gateway Adapter Adversarial & Contract Test Suite', async (t) => { ... })
   ```
   is counted as 1 test in the overall TAP summary. Inside this parent test block, exactly **35 subtests** (`await t.test(...)`) are registered and executed. Node's TAP summary reports:
   ```tap
   # tests 36
   # pass 36
   # fail 0
   ```
   The author of V8.32.78 copied the summary number `36` directly from the runner output, but only listed the 35 subtests in the detailed inventory.

2. **The "9b" Subtest Renumbering Shift:**
   In the source code (`pilot-contract-adapter.test.js`), subtest 10 was originally named `9b`:
   - Line 177: `'9. Invalid model identifier returns 503/400 MODEL_UNAVAILABLE'`
   - Line 191: `'9b. Generic local-model alias is rejected (must resolve to loaded model)'`
   - Line 205: `'10. Temperature outside allowed range...'`

### 5.2 Ten Mandatory Verification Scenarios

1. **Missing PSK:** Terminated at `authMiddleware` with HTTP 401 (`Missing internal service token`). `jsonParser` is never executed.
2. **Incorrect PSK:** Terminated at `authMiddleware` with HTTP 401 (`Invalid internal service token`). `jsonParser` is never executed.
3. **Correct PSK:** Passes `authMiddleware` constant-time hash check; proceeds to `jsonParser`.
4. **Bearer Authentication:** Extracted from `Authorization: Bearer <token>`; validated and accepted.
5. **Malformed Unauthenticated JSON:** Intercepted at `authMiddleware` with HTTP 401 before `jsonParser` runs. Verified by Test 31 (`assert.equal(res.statusCode, 401)`).
6. **Oversized Unauthenticated Payload (2MB):** Intercepted at `authMiddleware` with HTTP 401 before body buffering / HTTP 413. Verified by Test 32 (`assert.equal(res.statusCode, 401)`).
7. **Malformed Authenticated JSON:** Passes auth, reaches `jsonParser`, which catches SyntaxError and returns HTTP 400. Verified by Test 33 (`assert.equal(res.statusCode, 400)`).
8. **Oversized Authenticated Payload:** Passes auth, reaches `jsonParser` (`limit: '1mb'`), which throws `PayloadTooLargeError` returning HTTP 413.
9. **Unknown Routes:** No matching route; caught by default Express 404 handler.
10. **Alternate Routes to Inference:** Only `/v1/inference` and `/v1/pilot/inference` dispatch to LM Studio. Both enforce `authMiddleware, jsonParser`. Zero bypass routes exist.

*Clarification on Transport vs Application Buffering:* While Node.js TCP/HTTP socket layers buffer incoming bytes at the operating system socket level, Express's body parsing and JavaScript object allocation do not occur until `jsonParser` is invoked. Because `authMiddleware` terminates unauthenticated connections immediately with `res.status(401).json(...)`, unauthorized clients cannot trigger JSON parsing or CPU-intensive JSON tokenization.

## 7. Adversarial Fixture Path Audit (`pilot-001-runner.js`)

Inspection of `pilot-001-runner.js` lines 66–112 revealed critical path security nuances:

### 7.1 Path Traversal Analysis
```javascript
const candidatePath = path.resolve(approvedDir, path.basename(rawFixtureArg));
```
- **Detection vs Transformation:** The code does **NOT** detect traversal attempts in the argument string (e.g., `../../target.json`). Instead, `path.basename()` transforms and strips directory separators, reducing the path to `'target.json'`.
- It then evaluates `candidatePath = path.resolve(approvedDir, 'target.json')`.
- If `'target.json'` does not exist in `fixtures/pilot/`, it terminates with exit code 2: `FATAL: Fixture file not found in approved directory`.
- While effective at preventing directory escape, it silently coerces input rather than rejecting illegal characters.

### 7.2 Symlinks and Windows NTFS Junctions
- Handled at lines 80–95 via `fs.realpathSync(candidatePath)`.
- If a symlink or junction inside `fixtures/pilot/` targets an external location (e.g. `C:\Windows\System32`), `path.relative(realApprovedDir, realCandidatePath).startsWith('..')` evaluates to `true` and the process exits with code 2 (`FATAL: Path traversal detected`).

### 7.3 NTFS Hardlink Exposure (Vulnerability Analysis)
- In Windows NTFS (and Linux ext4), a **hardlink** is a directory entry pointing directly to an existing file record/inode.
- Unlike symlinks, a hardlink contains no target path information; all hardlinks to a file are indistinguishable peers.
- If an operator or script creates a hardlink inside `fixtures/pilot/test.json` pointing to an external file (e.g. a sensitive JSON configuration file on another drive), `fs.realpathSync()` resolves to `fixtures/pilot/test.json`.
- The relative path check does **not** fail (`path.relative` is `'test.json'`).
- If the external file name does not contain the blacklisted substrings (`whatsapp`, `.db`, `forensics`, `.sqlite`), the runner would read and send that file's contents as inference payload.

### 7.4 Architectural Recommendation for Real Pilot
Arbitrary file path arguments (`--fixture <path>`) should be **permanently eliminated**. The runner should only accept an enumerated fixture key (e.g. `--fixture-id SYNTHETIC_001`), loading a pre-approved in-memory fixture or verifying its SHA-256 against a hardcoded immutable registry before opening.
