## 1. Original Implementation Plan Deficiencies

An adversarial review of the previous revision of the implementation plan identified the following critical vulnerabilities and ambiguities:

| Defect ID | Original Deficiency | Security / Architectural Risk | Correction in V8.32.82 Plan |
| :--- | :--- | :--- | :--- |
| **DEF-01** | **Ambiguous Extraction Routing:** Plan suggested inferring extraction requests from output schema version or message content patterns. | An untrusted caller could submit an extraction request via legacy `/v1/inference` or unstructured channels, bypassing provenance and review checks while receiving unverified output. | Mandatory explicit task discriminator (`task_type: 'EXTRACTION'`) in `pilot-request-schema.json`. Legacy routes are completely decoupled from review creation and cannot emit extraction records. |
| **DEF-02** | **Source Text Co-Supply Risk:** Model or caller could supply `source_text` alongside extracted claims. | If an untrusted caller supplies both `source_text` and claims, provenance verification succeeds against forged source text rather than the immutable source record. | Enforce `SyntheticSourceRepository` as the sole authority. The Gateway retrieves `source_text`, message ID, conversation ID, and computes SHA-256 strictly within the trusted boundary. Caller/model-supplied text is rejected. |
| **DEF-03** | **Gateway Provenance Bypass:** `provenance-verifier.js` and `review-manager.js` were standalone modules not wired into `gateway-server.js`. | Gateway returned HTTP 200 `SUCCESS` for any JSON matching response schema without checking quote grounding or character offsets. | The 11-step mandatory extraction pipeline enforces `verifyExtractionProvenance` and schema validation before any HTTP 200 response can be emitted. |
| **DEF-04** | **Ephemeral Review Plane without Repository State:** Review record was created as a detached object during tests without repository storage or duplicate protection. | Untrusted callers could flood memory, overwrite records, or mutate returned review objects. | Creation of `ReviewRepository` with thread-safe in-memory map, duplicate rejection, defensive deep copies on insert/read, and strict `PENDING_REVIEW` invariant. |
| **DEF-05** | **Live LM Studio Test Dependencies:** Tests in `pilot-contract-adapter.test.js` called `http://127.0.0.1:1234`. Proposed runner command executed against live LM Studio. | Tests were non-deterministic, non-reproducible in CI, and violated the isolation policy by contacting live ports. | Implementation of deterministic in-process `lm-studio-mock.js`, removal of live runner command, and installation of a test-level network guard blocking `127.0.0.1:1234`. |
| **DEF-06** | **Equivocation of Exact Quote vs Semantic Truth:** Plan did not define whether exact quote verification guarantees factual truth. | Risk of mistaking verbatim character matching for semantic truth verification. | Explicitly documented limitation: Provenance verification guarantees verbatim textual grounding in the source text; it does **not** evaluate semantic entailment or external factual correctness. |

## 2. Final Execution Architecture

### 2.1 The Mandatory 11-Step Extraction Sequence

Every extraction request dispatched to the Gateway must complete the following atomic, fail-closed pipeline:

```
[Client / Runner]
       │
       ▼
 [Step 1: Authentication]
   ├── Validate x-internal-service-token via constant-time comparison
   │
 [Step 2: Request Validation]
   ├── Enforce task_type === 'EXTRACTION'
   ├── Validate against pilot-request-schema.json
   │
 [Step 3: Trusted Source Retrieval]
   ├── Query SyntheticSourceRepository by fixture ID / source_message_id
   ├── Reject any caller-supplied source_text or source_hash
   ├── Calculate SHA-256 of source_text inside application boundary
   │
 [Step 4: Model Inference]
   ├── Dispatch prompt to LM Studio (deterministic mock server during test)
   │
 [Step 5: Candidate Schema Validation]
   ├── Parse JSON response (or fenced code block)
   ├── Validate against pilot-candidate-extraction-schema.json
   │
 [Step 6: Forbidden-Field Rejection]
   ├── Reject output containing human_review, review_status, approval_status,
   │   approved, reviewer_id, reviewed_by, reviewed_at, is_approved, status
   │
 [Step 7: Source & Conversation ID Validation]
   ├── Validate candidate source_message_id against trusted repository record
   ├── Validate candidate conversation_id against trusted repository record
   ├── Reject any ID spoofing or mismatch
   │
 [Step 8: Provenance Verification of Every Claim]
   ├── Run verifyExtractionProvenance for every verifiable_claim
   ├── Verify verbatim quote match via UTF-16 code unit offsets
   ├── Enforce ALL-OR-NOTHING: If one claim fails, reject whole candidate
   │
 [Step 9: Trusted PENDING_REVIEW Record Creation]
   ├── Application code invokes createPendingReviewRecord()
   ├── Forces human_review.status = 'PENDING_REVIEW'
   │
 [Step 10: Repository Storage]
   ├── ReviewRepository.save(record)
   ├── Store deep copy; reject duplicate record IDs or message extractions
   │
 [Step 11: Success Response Delivery]
   └── Deliver HTTP 200 with candidate_id and review_status ONLY AFTER successful storage.
       If storage fails, emit HTTP 500. Zero partial acceptance.
```

### 2.2 Independent Review Plane Separation

- **Model Boundary:** Model output is strictly restricted to extraction claims (quote, offsets, extracted values). Any emitted fields attempting to assert review status, approval, or reviewer identity result in an immediate `SECURITY_VIOLATION` (HTTP 502 / rejection).
- **Application Boundary:** Only the trusted backend application assigns `PENDING_REVIEW`.
- **Review Repository:** In-memory store that holds unapproved candidates for future human operator inspection. Exposes no model-accessible approval operation.

## 3. Exact Files to Create or Modify

### 3.1 New Files

1. `orchestration/gateway/source-repository.js`
   - Defines `SyntheticSourceRepository`.
   - Hardcodes verified synthetic fixtures (`SYNTHETIC_001`, `SYNTHETIC_002`).
   - Retrieves authoritative text and computes SHA-256 within the trusted boundary.
   - Refuses caller-supplied text or foreign IDs.
2. `orchestration/gateway/review-repository.js`
   - Defines in-memory `ReviewRepository`.
   - Implements duplicate detection, defensive deep copying (`structuredClone`), `save()`, `getById()`, `listPending()`, `count()`, and `clear()`.
   - Guarantees stored records cannot be mutated by callers holding external references.
3. `orchestration/tests/mocks/lm-studio-mock.js`
   - Deterministic HTTP mock server providing `/v1/models` and `/v1/chat/completions`.
   - Supports configurable responses: valid structured extraction, verbatim quotes, malformed JSON, timeouts, 503 unavailability, and concurrency simulations.
4. `orchestration/tests/helpers/test-network-guard.js`
   - Test harness network interceptor that monitors `http`, `https`, and `net`.
   - Throws immediate uncatchable assertion if any socket or request targets `127.0.0.1:1234` or non-test endpoints.
5. `orchestration/tests/unit/adversarial-pipeline-integration.test.js`
   - Comprehensive adversarial test suite containing all 32 tests (20 mandatory + 12 additional adversarial scenarios).
6. `orchestration/tests/unit/runner-mock-integration.test.js`
   - End-to-end integration test executing `pilot-001-runner.js` against the mock gateway and mock LM Studio.

### 3.2 Modified Files

1. `pilot-request-schema.json`
   - Adds mandatory `task_type` discriminator property (`"INFERENCE" | "EXTRACTION"`).
   - Specifies conditional requirements when `task_type === "EXTRACTION"` (`source_message_id`, `conversation_id`, `synthetic_fixture_id`).
2. `orchestration/gateway/gateway-server.js`
   - Injects `sourceRepository` and `reviewRepository`.
   - Routes `task_type === 'EXTRACTION'` through the complete 11-step pipeline.
   - Rejects forbidden model fields, verifies claim provenance, and stores in review repository.
   - Preserves standard non-extraction inference untouched.
3. `orchestration/tests/unit/pilot-contract-adapter.test.js`
   - Updates live test cases (1, 23, 27) to bind to `lm-studio-mock.js` instead of live `127.0.0.1:1234`.
4. `pilot-001-runner.js`
   - Supports configurable gateway port for mock integration testing while preserving operator `--execute` safety flags.

## 4. Implementation Boundaries & Explicit Prohibitions

The following boundaries are absolute, immutable, and strictly enforced:

- **Zero WhatsApp SQLite Database Access:** No queries, connections, or schema assumptions against `whatsapp_forensics.db` or any real WhatsApp database.
- **Zero Real WhatsApp Message Processing:** All extraction is performed on synthetic fixtures only.
- **Zero Attachment Processing / OCR / Whisper:** Attachment processing, image extraction, OCR, and audio transcription are strictly prohibited.
- **Zero Real LM Studio Pilot Execution:** Testing must use `lm-studio-mock.js`. Calling `127.0.0.1:1234` or running live pilot commands is prohibited.
- **Zero External Inference / Zero Paid APIs:** No OpenAI, Anthropic, or cloud endpoints.
- **Zero Public Network Binding:** Gateway and mock servers bind strictly to `127.0.0.1`.
- **Zero Automatic Startup:** No background daemons or automatic process spawning without operator invocation.
- **Zero In-Place Source Modification Before Approval:** No code changes will be made until this plan is formally approved.
